# Design: Laya picks the screen, a live demo for Optus tech leaders

Generated by /office-hours on 2026-10-01

Repo: DrDonDon/soothsayer (design only; the POC itself lives outside this repo)
Status: APPROVED
Mode: Builder

## Problem Statement

A telco service app shows every customer roughly the same home screen. The idea: on
each app open, a small decision model reads a compact summary of the customer's state
and picks which **one of 10 front-end components** to show (add data pack, pay bill,
outage notice, and so on).

The proof of concept answers one question for Optus tech leaders: **can Laya make that
choice quickly, accurately and cheaply?** Comparison with Jev, a rules engine and a
general LLM is phase 2, not this POC.

## What Makes This Cool

- The "whoa" moment: drag a customer's data-usage slider from 40% to 95% and watch the
  phone mock swap from "usage meter" to "add data pack" fast enough to feel instant
  (target: under 150 ms on the laptop, shown live; vendor GPU figures are tens of ms),
  with Laya's confidence shown on screen.
- Laya does not write text, so it cannot hallucinate a component that doesn't exist.
  It scores the 10 options you give it and returns a probability for each, in one pass.
  That makes "pick 1 of 10" a classification problem, not a generation problem.
- Open weights (Apache 2.0, ~421M parameters, ModernBERT-large backbone). Vendor-reported
  p50 ~33 ms on a T4 GPU; ~13 ms on an M3 Max via the MLX port. The POC measures it
  independently on ordinary hardware.

## Constraints

- **Model:** Laya by Convai Innovations, `choice` question type. Request shape matches
  TypeSafe Jev's `system_one` API, so phase 2 can swap in Jev without changing the app.
- **Option budget:** all 10 component names + descriptions for one `choice` question
  must fit in `head_max_len` = **192 tokens**, i.e. about **19 tokens per component
  including its name and separators**. Laya throws if exceeded. Laya recommends fewer
  than ~20 options.
- **State budget:** customer state is truncated at **512 tokens** (English checkpoint).
- **Footprint:** ONNX weights ~1.7 GB fp32 (documented ~2 GB RAM for the model alone;
  measure real peak memory with the runtime and FastAPI on the demo laptop). Production
  would run on a server, not on the phone. The demo must say this out loud.
- **Data:** synthetic customer profiles only. No Optus customer data.
- **Form:** live demo only. No written benchmark report.
- **Hardware:** laptop (see Recommended Approach).

## Premises (agreed)

1. Picking a component is a 10-way classification over a compact customer state;
   Laya's `choice` question is the right fit.
2. The 10 component descriptions are the main tuning surface; they must fit 192 tokens
   and their wording will move accuracy more than anything else.
3. Customer state is compact synthetic JSON well under 512 tokens.
4. The demo includes a "run the scenarios" button: 30 pre-written scenarios with a
   human-expected component, played live with a running agreement counter.
5. Targets for "quick" and "cheap" are written down before the demo.
6. Below a confidence threshold, the app falls back to a safe default component, and
   confidence is shown for every decision.
7. Jev, rules and LLM baselines are phase 2. Keep the Jev-compatible request shape.

## Approaches Considered

- **A: Laptop minimal** (chosen). Python Laya reference + FastAPI + single HTML phone mock.
- **B: Cloud CPU service** (recommended by me, not chosen). Same demo on an AU-region
  CPU VM; gives real network latency and a measured cost per 1M decisions. Deferred to
  phase 2.
- **C: In-browser via onnxruntime-web** (rejected). Big wow, but a 1.7 GB first load on
  venue Wi-Fi and not representative of how a phone app would run it.

## Recommended Approach: A, Laptop minimal

```
 ┌──────────────── laptop ─────────────────────────────────────────┐
 │                                                                 │
 │  index.html (phone mock)          FastAPI  /decide              │
 │  ┌──────────────┐   POST state    ┌───────────────────────────┐ │
 │  │ sliders/      │ ─────────────▶ │ build choice question     │ │
 │  │ toggles       │                │ (10 components, ≤192 tok) │ │
 │  │               │ ◀───────────── │ laya.system_one(state, q) │ │
 │  │ [component]   │  component,    │ timing: server-side ms    │ │
 │  │ conf 0.91     │  probs, ms     └───────────────────────────┘ │
 │  │ [Run 30 ▶]    │                                              │
 │  │ 27/30 agree   │   scenarios.json (state + expected label)    │
 │  └──────────────┘                                               │
 └─────────────────────────────────────────────────────────────────┘
```

**Pieces**

1. `components.py`: the 10 components as `{name: description}`, plus checks using Laya's
   own tokenizer that the option block fits 192 tokens and every scenario state fits
   512 tokens (fail loudly, never silently truncate).
2. `decide()` wrapper: takes a profile dict, calls Laya with one `choice` question,
   returns `{raw_pick, shown_component, probabilities, confidence, fell_back,
   latency_ms}`. If top probability < threshold, `shown_component` = Account overview
   and `fell_back` = true; `raw_pick` is always Laya's top choice. Shaped so a
   `JevDecider` can implement the same interface in phase 2.
3. `scenarios.json`: 40 synthetic profiles, each `{id, state, expected, reason,
   ambiguous: bool, competing: [components], split: "tune" | "holdout"}`. 30 are the
   live set; **10 are a hold-out never used for wording or threshold tuning**. About
   6 of the 30 (and 2 of the 10) are ambiguous (e.g. unpaid bill AND active outage).
4. `index.html`: phone-shaped mock rendering the shown component as a realistic card,
   with sliders/toggles for the profile, a confidence badge, a latency readout, and the
   "Run scenarios" button that steps through them with a running agreement counter and
   highlights misses. All assets local (no CDN fonts or scripts).

**How priority reaches Laya.** Laya scores each component's description against the
state; it has no separate rules input. So precedence is written into the descriptions
themselves where the budget allows (e.g. Outage: "...takes priority over billing and
usage"). The ambiguous scenarios then test whether Laya applies it unaided, and misses
there are a reported finding, not hidden. If ambiguous agreement is poor, the
documented fallback design is **detect + policy**: ask Laya 10 yes/no (`noul`)
questions in the same single pass ("does an outage apply?") and let the written policy
pick the highest-priority "yes". Run both in the CLI and report both; the demo shows
whichever the room should see, labelled honestly.

**Scoring rule.** Accuracy = Laya's `raw_pick` vs the human label. Separately report:
misses caught by the fallback (raw wrong, fell back) and correct answers suppressed by
the fallback (raw right, fell back).

**Fallback in the mock.** When the fallback fires the phone shows Account overview with
a grey "unsure" badge, and the presenter panel beside the phone shows Laya's raw pick
and its probability. The scenario runner marks it as "fell back".

**Slider behaviour.** Debounce slider input (~150 ms after the last change); each
request carries a sequence number and the UI ignores any response older than the
latest. No out-of-order flicker.

**Profile schema and controls** (one field per component trigger):

| Field | Mock control | Drives |
|---|---|---|
| `data_used_pct`, `day_of_cycle` | sliders | Usage meter, Add data pack |
| `bill.status` (paid/due/overdue), `bill.days_to_due` | toggle + slider | Pay bill now |
| `bill.last_amount` vs `bill.avg_amount` | slider (last amount) | Bill explainer |
| `network.outage_at_address` | toggle | Outage notice |
| `network.dropouts_7d` | slider | Troubleshoot service |
| `travel.overseas`, `travel.roaming_active` | toggles | Roaming pack |
| `contract_months_left`, `device_age_months` | sliders | Upgrade offer |
| `support.failed_self_service_7d`, `support.contacts_30d`, `support.open_complaint` | slider + toggle | Talk to us |
| `recent_app_actions` (capped at 5) | preset buttons | context for all |

**Draft component set** (to confirm; see Open Questions)

| # | Component | Shown when (name + description ≤ ~19 tokens together) |
|---|---|---|
| 1 | Account overview | nothing notable; the safe default and fallback |
| 2 | Data usage meter | moderate usage, mid-cycle, no action needed |
| 3 | Add data pack | near or over data allowance before cycle ends |
| 4 | Pay bill now | bill overdue or due within days, unpaid |
| 5 | Bill explainer | latest bill much higher than usual |
| 6 | Outage notice | active network outage or degraded service at their address |
| 7 | Troubleshoot service | repeated drop-outs or slow speeds, no known outage |
| 8 | Roaming pack | overseas or travel booked, no roaming pack |
| 9 | Upgrade offer | contract ending or device old, eligible to upgrade |
| 10 | Talk to us | recent failed self-service, complaint, or repeated contact |

**Priority policy** (the "right answer" when several apply): Outage > Pay bill >
Bill explainer > Talk to us > Troubleshoot > Add data > Roaming > Upgrade > Usage meter
> Account overview. Without a written policy, scenario labels are opinion and
"accuracy" means nothing.

**Example state** (well under 512 tokens):

Expected: **Add data pack**.

## Success Criteria (proposed targets, set before the demo)

- **Accurate:** raw agreement ≥ 26 of 30 on the live set (~87%) and ≥ 8 of 10 on the
  hold-out. Ambiguous scenarios reported separately (target ≥ 4 of 6). The demo says
  the 30 were used for tuning and the 10 were not. Misses are shown, not hidden.
- **Confident when right:** at the chosen threshold, ≥ 90% of correct raw picks stay
  above it and ≥ 50% of misses fall below it (fallback catches them). Threshold chosen
  on the tuning split only.
- **Quick:** warm p95 under 150 ms for the Laya call alone (timed server-side around
  the model call), measured over 500 sequential single decisions cycling through the
  scenarios after 20 discarded warm-up calls, with ONNX/PyTorch thread count recorded.
  End-to-end (browser to screen) shown live separately. Cold start reported separately.
- **Cheap:** throughput = sequential single decisions per second on the laptop at the
  same thread setting (batch size 1, concurrency 1), plus one run at concurrency 4.
  Cost per 1M = (named cloud instance $/hour ÷ 3600) ÷ throughput × 1M, assuming the
  instance's vCPUs match the laptop's thread count. Labelled as an estimate until
  phase 2 measures it on a real VM.
- **Honest framing:** the demo states "runs on a server in production, ~1.7 GB model,
  not on the phone."

## Open Questions

1. Are these the right 10 components for the Optus app, or do you have a real list?
2. Who labels the 30 scenarios, and does a second person agree with the labels?
   (If two humans only agree 80% of the time, 87% for Laya is a strong result.)
3. Python reference package (PyTorch checkpoint) vs `@receptron/laya` (Node, ONNX
   Runtime, fp32 ONNX): pick whichever runs cleanly on your laptop. Python is canonical;
   the Node port matched it to 4 decimal places. Record which runtime and weight format
   produced the numbers.
5. If the latency spike misses 150 ms: try thread tuning, then an int8-quantised ONNX
   export (re-check accuracy), then a shorter state. If still over, revise the target
   and say why.
4. Single English checkpoint vs multilingual checkpoint: English is fine for the demo
   unless you want to show a non-English profile.

## Distribution Plan

Local only: a git repo with `make fetch` (run once, online: downloads and pins the Laya
weights to a fixed revision) and `make demo` (offline: loads from the local directory
with Hugging Face offline mode forced, starts FastAPI, opens `index.html`). The demo
must work with Wi-Fi off. No CI/CD for the POC.

## The Assignment

Before writing any code: sit down with one colleague who knows the Optus app, agree the
10 components and the priority policy, then each of you label the same 40 scenarios
separately. Count how many you agree on. That number is the realistic ceiling for
Laya, and it's the first thing to say in the room. Then settle each disagreement:
discuss and agree, or amend the priority policy; a scenario you still can't agree on
gets dropped. Freeze the labels before Laya sees any of them.

## Next Steps

1. Latency spike (first hour): load Laya on the demo laptop, time 500 warm decisions on
   a dummy profile, record p50/p95 and peak memory. If it misses 150 ms, work through
   Open Question 5 before anything else.
2. Write the 10 component descriptions and the priority policy; run the 192-token check
   with Laya's tokenizer. Tighten wording until it fits.
3. Write, label and adjudicate the 40 scenarios (see The Assignment); mark ambiguous
   ones and the 10-scenario hold-out.
4. Build `decide()` and a CLI that runs the tuning set and prints agreement, ambiguous
   agreement, fallback catches/suppressions and latency. Iterate on descriptions here,
   before any UI. Try the detect + policy variant if ambiguous agreement is poor.
5. Pick the fallback threshold on the tuning set, then run the hold-out once.
6. Build the phone mock with sliders, the confidence badge and the scenario runner.
7. Dry-run with Wi-Fi off. Rehearse the "what about cost at scale?" answer using the
   estimate, and say that phase 2 measures it on a VM alongside Jev and the baselines.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

### R2-1 — completeness

**Problem**

> The profile schema still does not cover every trigger written into the component descriptions. Roaming pack fires on 'overseas or travel booked' but there is no travel-booked field; Troubleshoot mentions 'slow speeds' and Outage mentions 'degraded service' with no corresponding fields; Upgrade offer requires 'eligible to upgrade' with no eligibility field. Laya is told to look for facts the state can never contain, and scenarios that rely on them cannot be expressed.

**Remedy**

> Either add fields (e.g. travel.trip_booked_days_out, network.speed_degraded, upgrade_eligible) with mock controls, or reword the descriptions so they only reference fields that exist in the schema.

### R2-2 — consistency

**Problem**

> The adjudication rule drops scenarios the two labellers cannot agree on, but the success targets are absolute counts tied to fixed set sizes (>= 26 of 30, >= 8 of 10, >= 4 of 6 ambiguous) and the ambiguous count is only 'about 6'. After any drop, or if the ambiguous count is not exactly 6, the targets no longer describe the set being scored.

**Remedy**

> Express targets as percentages of the frozen set (or require replacing dropped scenarios with newly adjudicated ones so the 30/10 split and exactly 6 ambiguous live scenarios are preserved), and fix the ambiguous counts once labels are frozen.

### R2-3 — consistency

**Problem**

> The whoa moment promises a swap 'fast enough to feel instant' with a 150 ms target shown live, but the slider is debounced ~150 ms after the last change before a request is even sent. Perceived latency is therefore debounce + network + model (plausibly 300 ms or more), and the on-screen latency readout's meaning (model-only or end-to-end) is not stated.

**Remedy**

> State what the latency readout shows (server-side model ms vs end-to-end from request), and either shorten the debounce / use throttle-with-trailing-call while dragging, or reframe the whoa claim so the visible delay is not presented as the 150 ms figure.

### R2-4 — consistency

**Problem**

> The detect + policy variant is described both as always run ('Run both in the CLI and report both') and as conditional ('Try the detect + policy variant if ambiguous agreement is poor', Next Step 4; 'If ambiguous agreement is poor, the documented fallback design is...').

**Remedy**

> Choose one: always build and report both variants, or build detect + policy only if a stated ambiguous-agreement threshold is missed.

### R2-5 — clarity

**Problem**

> 'The demo shows whichever the room should see' gives no selection criterion for choosing between the choice-question variant and detect + policy. Choosing after seeing results (especially hold-out results) turns the hold-out into a selection set and invites cherry-picking.

**Remedy**

> Define the selection rule (e.g. higher tuning-set agreement, ties to the simpler variant) and require the choice to be made on the tuning split before the single hold-out run.

### R2-6 — completeness

**Problem**

> The detect + policy variant has no defined confidence, fallback or scoring behaviour. With 10 independent yes/no probabilities, it is unspecified what 'confidence' the badge shows, when the Account overview fallback fires (e.g. no 'yes' above threshold), what raw_pick means, and how the 'Confident when right' targets apply.

**Remedy**

> Define for detect + policy: the yes threshold, the reported confidence (e.g. probability of the chosen 'yes'), the fallback condition, and that decide() returns the same fields so scoring and the mock work unchanged.

### R2-7 — feasibility

**Problem**

> The claim that 10 `noul` questions can be asked 'in the same single pass' is unsupported; the document only establishes single-pass scoring for one `choice` question. If each question requires its own forward pass, detect + policy costs up to 10x latency and breaks the 150 ms and cost targets.

**Remedy**

> Verify in the latency spike whether multiple questions share one encoder pass, and state the expected latency of detect + policy (or that its latency is measured and reported separately).

### R2-8 — feasibility

**Problem**

> Open Question 3 allows the Node `@receptron/laya` port, but the committed architecture is a Python FastAPI server calling `laya.system_one`. If the Node runtime is chosen, there is no stated way for FastAPI to call it, and the int8-quantised ONNX remedy in Open Question 5 likewise only applies to the ONNX path.

**Remedy**

> Either commit to the Python package for the POC (keeping Node as a fallback only for numbers comparison), or state that choosing Node replaces FastAPI with a Node HTTP server exposing the same /decide contract, and note which latency remedies apply to which runtime.

### R2-9 — feasibility

**Problem**

> `make demo` 'opens index.html' but it is not stated whether the page is served by FastAPI or opened from file://. A file:// page POSTing JSON to localhost /decide will be blocked by CORS unless the server allows it, which would fail on stage.

**Remedy**

> Have FastAPI serve index.html and its local assets from the same origin (or explicitly enable CORS for the page's origin).

### R2-10 — clarity

**Problem**

> The cost formula's inputs are not pinned: no cloud instance or $/hour is named, and the concurrency-4 throughput run is measured but its role in the cost estimate is undefined (the formula uses a single 'throughput').

**Remedy**

> Name the instance type and price used for the estimate and state which throughput (concurrency 1 or 4) feeds the formula, with the other reported as context.

### R2-11 — feasibility

**Problem**

> The cost estimate assumes cloud vCPUs match laptop threads one-for-one, ignoring large per-core performance differences (e.g. Apple M-series cores vs hyperthreaded cloud vCPUs), so the estimate can be off by a large factor without that being disclosed.

**Remedy**

> State the laptop CPU model, note that per-core speed differs from the named instance, and present the cost as a range or with an explicit caveat until the phase 2 VM measurement.

### R2-12 — clarity

**Problem**

> It is unclear whether the hold-out is shown in the room. The mock's runner is labelled 'Run 30' and the diagram references only the 30, yet the demo is to say the 10 were not used for tuning, implying a hold-out result is presented; Next Step 5 says the hold-out is run 'once' in the CLI.

**Remedy**

> State whether the demo replays the hold-out live in the runner (as a separate, labelled set) or reports the frozen CLI hold-out result, and how its agreement is displayed.

### R2-13 — consistency

**Problem**

> Open Question 2 still refers to labelling 'the 30 scenarios' while scenarios.json, The Assignment and Next Step 3 all specify 40 scenarios (30 live + 10 hold-out).

**Remedy**

> Change Open Question 2 to the 40 scenarios (or note it is now answered by The Assignment).

### R2-14 — clarity

> Open Questions are numbered out of order (1, 2, 3, 5, 4), and item 5 is a committed contingency plan referenced by Next Step 1, not a discovery question, blurring open questions with committed behaviour.

1. [P1] (confidence 8/10) Design Pieces 2 / Success "Cold start reported separately": nothing says when the 1.7 GB model loads. If it loads lazily, the first slider drag in the room stalls for seconds. **Required by approved contracts:** load and warm up (20 discarded calls, as already specified) in FastAPI startup; `/health` returns ready only after warm-up; the page shows "warming up" until ready.
2. [P2] (8/10) Scenario runner and slider can both call `/decide`; concurrent PyTorch calls oversubscribe CPU threads and pollute the latency numbers. **Required by the approved measurement contract:** sync endpoint, one process-wide lock around the model call; timing measured inside the lock.
3. [P2] (8/10) No behaviour when the server is down or returns an error: the phone would keep showing a stale card silently. **Edge case, in scope:** grey out the card with a "Laya offline" banner; scenario runner stops and reports the failed scenario.
4. [P3] (9/10) Bind to 127.0.0.1 only; synthetic data, but no reason to expose a port on venue Wi-Fi.
